# Lumine repository instructions

## The North Star — read this first

> **Lumine should feel like a companion living quietly on the computer, not an
> application the user has to open.** She should sleep when not needed, hear when
> called, appear when addressed, understand the complete request, act when
> authorized, communicate naturally, and disappear again when the interaction is
> over. **The full UI is her home, not her existence.**

Four documents define the product, and every change in this repository is judged
against them:

| Document | What it decides |
| --- | --- |
| [`VISION.md`](VISION.md) | What Lumine is, what she is not, the success criteria, and the surface-routing rule |
| [`ARCHITECTURE.md`](ARCHITECTURE.md) | The nine runtime layers, the process model, the lifecycle state machine, the IPC contract, wake and island design |
| [`ROADMAP.md`](ROADMAP.md) | Phases 0–9 **of the companion track**, with observable exit criteria and what each phase deliberately does not build |
| [`docs/agent-runtime/`](docs/agent-runtime/README.md) | The **runtime track** — goals, phases 0–10, and the definition of done for the internal agent runtime |
| [`docs/decisions/`](docs/decisions/) | Fourteen ADRs — load-bearing choices, the alternatives that were refused, and the conditions that would reverse them |

Supporting: [`docs/gap-audit.md`](docs/gap-audit.md) measures the vision against the
current code, with the conflicts named; [`docs/plans/wave-1-always-on-runtime.md`](docs/plans/wave-1-always-on-runtime.md)
is the detailed Phase 1 plan.

**The most important architectural facts about the code today**, all of which are
invisible from reading any single module:

- The app's lifetime is currently the runtime's lifetime. `lib.rs` stops the worker
  on `ExitRequested`, and nothing but a button press starts it. The vision requires
  the opposite, and that inversion is Phase 1's first task.
- **The microphone only exists inside a LiveKit session.** The webview publishes it
  (`setMicrophoneEnabled`); the Python worker opens no audio device. Anything
  "always on" needs its own capture path.
- There is **no** autostart, **no** tray, **no** second window, **no** window-API
  usage in the frontend, **no** wake word and **no** idle timeout anywhere.
- `AgentState::Sleeping` means "there is no worker process", which is the *opposite*
  of the vision's `SLEEPING`. Process state and companion state must stay separate
  types ([ADR-0012](docs/decisions/0012-process-vs-companion-state.md)).
- The session greeting is **unconditional**, which fights the one-shot requirement
  ([ADR-0013](docs/decisions/0013-greeting-conditional.md)).

### Pre-flight for any change

Before implementing a feature, answer in order — and write the answers down if the
answer is not obvious:

1. **What user problem does this solve?** Anything that does not answer is a demo.
2. **Which phase does it belong to?** A later-phase feature implemented early will
   be built on assumptions later phases invalidate.
3. **Which surface?** Island, full UI, tray, or voice. "The full UI, because that is
   where the code is" is not an answer — see the routing table in
   [`VISION.md`](VISION.md).
4. **Does it conflict with a recorded decision?** If it does, supersede the record
   explicitly, in writing, with a reason. Do not delete decision files.
5. **Is a new subsystem or dependency necessary?** Check first whether an existing
   one already owns the responsibility ([ADR-0010](docs/decisions/0010-layer-ownership.md)).

Build one vertical slice at a time ([ADR-0011](docs/decisions/0011-no-overbuild.md)).
The roadmap preserves direction; it does not authorise work.

## Scope and source of truth

- This repository has two independently runnable parts: `agent/` is the Python LiveKit worker; `lumine-ui/` is the React/Vite UI inside a Tauri/Rust shell. There is no root workspace or task runner.
- The root `package.json` has no app scripts. Run frontend/Tauri commands from `lumine-ui/`; the app entry is `src/main.tsx` → `src/App.tsx` → `src/pages/Home.tsx`.
- Treat manifests, environment examples, and current source as authoritative when prose conflicts. The root [`README.md`](README.md) describes the shipped state and links to both tracks; some checked-in `docs/`/nested `AGENTS.md` notes describe earlier scaffold states.
- **Two tracks, two roadmaps.** [`ROADMAP.md`](ROADMAP.md) is the companion track (wake, island, lifecycle, memory, proactive). [`docs/agent-runtime/`](docs/agent-runtime/README.md) is the runtime track (router, task model, executor, verification, permissions, persistence). A change belongs to one; check which before assuming a phase number.

## Runtime shape

- `agent/agent.py` is the worker entrypoint. It loads the persona and `agent/.env` by file path, runs a persistent LiveKit `AgentServer` named `lumine`, and creates a new `AgentSession` for each dispatched room.
- The current React voice flow is in `lumine-ui/src/features/voice/voice-manager.ts`: make sure the Python worker is running, create a fresh room, request a token through Tauri, connect, enable the microphone, dispatch `lumine`, consume agent audio/transcripts/emotion/notice events, then remove listeners, stop media, disconnect, and delete the room.
- `lumine-ui/src-tauri/src/agent_manager.rs` implements child-process start/stop/restart and worker-readiness commands. The React voice path now calls `start_agent` and then `wait_for_agent_worker` before dispatching, so the app owns the worker's lifecycle and the worker reads the config the UI writes plus any keyring credentials. A readiness timeout is logged rather than fatal: a worker started outside Tauri is invisible to Rust and can still serve the room. When testing settings changes, stop any `lk agent dev` worker first — the two briefly coexist and LiveKit dispatches to only one of them.
- A separately started worker still reads settings saved from the UI. `config_store.config_path()` searches `LUMINE_CONFIG_PATH`, then the desktop app's local data directory, then `agent/lumine.config.json`; the desktop directory is what the Tauri side writes to. `validate_config.py --describe` reports `source`, `configPath`, and `searchedPaths`, and the worker emits `config_path` on `config_applied`/`config_rejected`, so a worker that is reading the wrong file says so instead of silently using `agent/.env`.
- Python worker stdout uses `LUMINE_EVENT <json>` records. Rust re-emits them as Tauri events; current event names use underscores (`agent_started`, `agent_state_changed`, `agent_stopped`, `agent_error`, `agent_runtime`), not dotted names.
- `ConversationPanel` stays backend-agnostic. `useConversation` has a `ConversationService` seam and currently defaults to the empty mock service; live voice messages enter through the callbacks wired in `Home.tsx`.

## Agent tools

- `agent/agent.py` passes `get_tools()` to the `Lumine` agent. The registry in `agent/tools/tools_registry.py` is the source of truth for registered tools; tool docstrings are the model-facing schema.
- Current tool IDs are `get_weather`, `get_news`, `search_web`, `recall_persona`, `find_app`, `open_app`, `manage_window`, `desktop_control`, `browse`, `run_task`, `web_control`, `cancel_task`, `play_media`, `whatsapp_read`, `whatsapp_chats`, `whatsapp_account`, and `send_whatsapp`, registered cheapest-first across five categories (Web, Internal, Media, Messaging, Desktop). `agent/tool_catalog.py` is the authority — it prints the live list, and `--check` fails on a tool with no card.
- **`desktop_control` is the mouse and keyboard, for any application without a dedicated tool of its own.** It is the fallback rather than a replacement — a blind click is less reliable than a real selector, so a window with its own tool *keeps* it — but nothing is walled off. Lumine has hands, and the only refusal left is her **own** window, because an agent that can click anything can click the Tools page and switch itself off mid-turn. Three rules carry it, and none of them is a prompt instruction:
  - **"The screen" is never the foreground window.** `capture.candidate_windows()` filters for usefulness rather than z-order. While you are *talking* to Lumine the foreground window **is Lumine**, and an always-on-top clock widget takes it without you doing anything and exposes zero controls — either one read as "a blank page" with Notepad right behind it. `best_window()` takes the first candidate that actually exposes a control.
  - **An integrated window is a hint, not a veto.** `tools/desktop/ops.py::INTEGRATED_WINDOWS` matches the *window's own* process — never a prefix and never a child, because `msedgewebview2.exe` is the renderer inside every Tauri and WinUI app and a prefix match reports Lumine's own window as a browser. The router prefers the dedicated tool and the approval card names it ("web_control would be steadier here"), but nothing stops an act. It was a hard refusal, and that turned the fallback into a wall.
  - **A structural refusal on a password field**, checked before the gate, so no approval question can unlock it. Everything else runs — `click`, `type`, `scroll`, `move`, `drag`, `right_click` are all `act`. Only a control whose *own name* reads as destructive or irreversible, and `press` (Enter is a submit), ask.
  - **`uia.is_our_own` covers the desktop shell, not just the worker.** They are separate processes, so a pid-only comparison against `os.getpid()` never matched the app's own window and the guard did nothing. `_own_process_ids()` walks the parent chain while it is named `lumine`/`lumine-ui` and stops at anything else.
- **The UI Automation harness is `tools/desktop/uia.py` and is shared.** `messaging/whatsapp_desktop.py` keeps `_driver`, `_run`, `_keystrokes` and `_texts_of` as aliases onto it, so there is one worker thread, one COM apartment per thread, one deadline and one cooldown. A WhatsApp call that overruns therefore cools down the desktop path too, which is correct: the worker is one thread and is genuinely stuck.
- **Freshness is a second reading, never a token.** `capture.confirm_target` re-walks the tree and re-finds the target *by role and name* before any irreversible act, and refuses when the control is gone, renamed, or moved. A generation comparison cannot do this, because the tool supplies that number itself: `check_generation` inside one call is `x == x` and always passes, and it survives only in `run_task`, whose steps genuinely span a gap. The token's remaining job is to identify *which* look of the screen a number came from, so the tool result and the UI panel can be checked against each other. The smoke test found the vacuous check; every unit test had fed it a number from `_LAST`.
- **Every child window is walked, not just the top-level handle.** Electron, WinUI and every Chromium shell put their content in a child window (`Chrome_RenderWidgetHostHWND`), leaving the parent's tree holding the title bar and nothing else — a parent-only walk reported VS Code as three corner buttons. Measured on a real window; a fake tree has no child windows, so no unit test would have caught it.
- **`run_task` drives it, in two steps.** `desktop_observe` and `desktop_act`, with the act `depends_on` the observe. `router.py` routes an interaction that names no target to the desktop rather than asking "which website?" — the wrong question for "click the save button". `STEP_ACTION_CLASS["desktop_act"]` is `sensitive` because its class is computed from the element, and a plan must not be able to describe a Delete click as an ordinary one.
- **`play_media` is the music library, and it ships on.** Seven verbs — `find`, `search`, `play`, `next`, `previous`, `stop`, `folders` — over the one folder granted in Settings → **Permissions**. Six rules carry it:
  - **The folder is the entire boundary, and both sides of the comparison are resolved.** `library.resolve_track` is a second *consumer* of the shape `messaging/whatsapp_files.py` already uses for attachments: resolve first, then compare, so `..`, an absolute path and a symlink pointing out all land in the same refusal. A caller-supplied root is resolved too — that omission made `scan(root=…)` return nothing at all under a Windows short `8.3` path, silently.
  - **`library_root()` reads the saved document; the environment is the fallback.** It read only `LUMINE_MEDIA_LIBRARY` at first, while the Permissions screen writes `media.library` into the document, and nothing bridged the two — so **choosing a folder in the app did nothing for the worker**. Measured: five consecutive voice requests came back "You haven't picked a music folder yet" *with the tool visibly enabled*, which is the worst shape that bug could take, because the Tools page said the capability was on while every call failed.
  - **`media.enabled` ships ON, and still fails closed.** `tools.<id>` only ever reduces authority so an instruction it did not understand reads as `on`; this one *grants* a capability, so an unrecognised value reads as `off` and `settings/validation.py` treats it as an **error**. Defaulting *on* does not change that: only an **absent** value reaches the default, because falling through on a misspelling would mean `LUMINE_ENABLE_MEDIA=enabled` turned it on — the exact inverse of what was meant. It ships on because the capability is bounded where `desktop.input` is not: one allowlisted folder, and no verb that moves, renames or deletes. A fresh install gets no folder, so the honest default state is "on, with nothing to reach yet".
  - **Nothing on the music path loads a track list into the frontend.** There is no Music settings tab and no library browser: a filename is not a setting, and a text box matching characters is strictly worse than Lumine matching the words you *said*. `musicClient.ts` lost `searchMusic` / `playTrack` / `MusicHit` / `MusicSearch`, `media_probe.py` lost `tracks`, and the Rust commands `search_music` and `play_music_track` are gone — and so, with the Focus workspace's removal, are `canonical_library_root`, `validate_against_library` and `is_in_app_audio`, the `media.rs` helpers its in-app player needed. What the app shows instead is a **widget** on the home page (`widgets/LocalWidgets.tsx::MusicWidget`) that reads the folder's name out of the saved document — the last path segment of a string it already has, so **it starts no subprocess** — plus a **Permissions** settings section that owns the only part that genuinely is a permission.
  - **The spelling tolerance is the WhatsApp matcher, imported.** `match.py` reuses `whatsapp_flow._same_word_spoken_two_ways` / `_edit_distance` rather than writing a second edit-distance tuned for filenames. What is genuinely new for files: **version tags** (`vocal`, `no-music`, `acapella`) are split out of the filename and matched on a separate axis, so *"play the Akhon Ami vocal song"* reaches `Akhon Ami (Vocal).mp3` and "play the instrumental version" cannot be answered by the vocal; **partial matching** on *more than half* the query's words; and `Hit.confidence`, one number folding tier and coverage together so "act or ask" is decided like-for-like. Two of those were bugs first: a title-only matcher reported `vocal` as *missing* on a file that is a vocal (the word had been deliberately removed from the title), and comparing raw coverages let a tag-only hit outrank a real title match, so the exact request in the brief came back as "which of these nine?".
  - **A folder is a queue, and this is the whole of the incident fix.** A reported failure was *"when I said play the vocal songs it played all 9 at once, no queue or anything, I couldn't able to hear anything."* `os.startfile` takes **one** file and the OS owns it from there, so the only way to play nine was to start nine. `tools/media/queue.py` now writes one `.m3u8` from already-validated paths and opens **that**; the player's own window owns the order, which is also where skip, pause and stop live. Nothing is bundled — the player that was going to open the first song opens the list instead. One track is opened **directly**, because a one-track queue is one indirection for nothing and `queued: false` has to be true. Queues are named by a hash of their body (idempotent, no accumulation), written outside the library so the next scan cannot offer one as a track, `.m3u8` rather than `.m3u` because the latter is read as the local codepage and turns a Bengali title into mojibake in the player's own list, and a title's newlines are stripped because there is no escape in the format and one would stand up a second `#EXTINF`. `agent/media_queue.py` is the widget's second caller of the same `queue.build` — two processes cannot call each other, so they share a builder rather than an implementation.
  - **The widget's Play all is not the voice path.** `queue_music` opens a queue with no permission gate, on purpose: the gate asks "may Lumine do this", and the person clicking has already answered a different question. The webview only ever supplies a **subfolder name** — never a path — and the script resolves the library root from the saved document itself, so `scanner.is_inside_library` is what stands between the page and a filename.
  - **She cannot stop it, and says so.** This process holds no handle to what it launched, and now that a folder is a queue the honest sentence is narrower and better: skip, pause and stop are **the player's controls over its own list**, and the result says so. `stop` names the last track she queued, which is the useful half — "stop the music" with four player windows open is otherwise unanswerable. `next`/`previous` *are* possible because playing a file is the one thing here she can do; `player.Player` is the seam, and `SystemPlayer` is `os.startfile`. No player is bundled, and no verb moves, renames or deletes anything.
- **To test it:** `python agent/desktop_probe.py` (read-only: what this window exposes) and `python agent/desktop_smoke.py` (staged; read-only by default, `--stage full` moves the mouse). `docs/desktop-control-testing.md` is the workflow, and it explains how to read a failure rather than only that one happened.
- **Every tool has an on/off switch on the Tools page**, written to `tools.<id>` in the saved document. It is a document key rather than an environment variable because it is the one toggle a settings screen has to be able to write *and revoke*. `LUMINE_DISABLED_TOOLS` (comma-separated exact ids) and `LUMINE_ENABLE_APP_LAUNCH` / `LUMINE_ENABLE_BROWSER` stay underneath it, resolved per key — the same precedence `messaging.whatsapp.mode` uses. An unrecognised value is read as `on`, because this key only ever *reduces* authority; `messaging.whatsapp.mode` fails closed on purpose, and the two are deliberately not consistent. `settings/validation.py` checks the shape and never the ids, because it does not import the registry (the registry reaches the permission gate, which reaches settings); `tool_catalog.py --check` reports a switch for a tool that does not exist. The switch takes effect on the **next call** — `get_tools()` runs per dispatched room, so no worker restart is involved.
- **`desktop.input` is the only switch that ships `off`** (it used to be one of two), with `LUMINE_ENABLE_DESKTOP_INPUT` underneath it and the document winning per key. `desktop_control` is excluded from `LUMINE_ENABLE_APP_LAUNCH` deliberately: launching a program and driving one are different amounts of authority. An unrecognised value here reads as `off`, which is the opposite of `tools.<id>` on purpose — that key *reduces* authority and this one *grants* it, so the two fail in opposite directions, and `settings/validation.py` treats a bad value as an **error** rather than the warnings it uses elsewhere, because a silent miss here removes a capability from a document that looks correct. `test_tool_catalog.DEFAULT_OFF_TOOLS` is a map, so a reason can name the switch that actually turns it on, so a *new* tool defaulting to off has to be listed there with a reason a user can act on.
- **Browser actions address the node the ranking chose**, by a `data-lumine-ref` marker the collection script stamps on each control, not by rebuilding a selector after the fact. `tools/browser/locators.py` filters by **role** as well as by name, which is what makes "the second video" the second *link* rather than the second control on the page — a search button, a cookie banner, a header menu item. `tools/browser/sites.py` holds how YouTube, Google, Maps and the rest are searched, and a search is one step that types *and submits*: splitting those is how a search used to end with the text typed and nothing run.
- **The orchestration layer** is `runtime/router.py` (pure: request + machine facts -> environment), `runtime/task_model.py` (Task/Step, dependencies, retry, cancellation) and `runtime/task_engine.py` (deterministic progression, checkpoints, bounded concurrency). `tools/task_runner.py` is the `run_task` / `cancel_task` tool that meets them. It is the right tool for **anything with two or more dependent steps**, and the single-purpose tools remain right for one. The router's rules are ordered by strength: an explicit environment claim ("in your browser", "on my desktop") beats everything; then a named installed program; then a named site; then an address; then the verb family. With two equally supported environments it asks rather than opening two things. Routing preferences live at `desktop.browsers` in the saved document (`default`/`desktopBrowser`, `preferOwnBrowser`) with `LUMINE_DEFAULT_BROWSER` and `LUMINE_PREFER_OWN_BROWSER` underneath, and are validated by `settings/validation.py`.
- **`runtime/verification.py` is the vocabulary every side-effecting operation reports in**: `requested`, `dispatched`, `accepted`, `observed`, `failed`, `timed_out`, `uncertain`. The ladder only goes up on evidence — `observed` implies the three below it, and nothing implies `observed`. `uncertain` is the load-bearing one: it is the only value that makes a retry a *decision* rather than an accident, and a launch with no window in sight is `accepted`, never `observed`.
- **`tools/app_resolver.py`** turns a spoken name into one target and then checks the launch: window first (a running process is not a window), index entry second, and after starting anything it waits for a window to appear. `new_instance` is the only thing that authorises a second window and is never inferred. It classifies a window as `program`, `browser` or `web_app` — the last from the *site's* title, which is what stops an installed Instagram PWA being reported as Chrome.
- **`web_control`** is the semantic sibling of `browse`: it finds a control by role and name (`tools/browser/locators.py`), resolves ambiguity into candidates instead of guessing, and re-checks the page after every action. `tools/browser/state.py` owns the snapshot generation that makes "observe, act" mean what it says. `tools/browser/youtube.py` holds the result-selection rules — filter by every constraint the user gave, prefer an exact channel, *then* apply the position — and never constructs a watch URL.
- Every tool call passes `agent/runtime/permission_gate.py`. Each tool has an in-code action class — `read`, `act`, `sensitive`, or `destructive` — that the saved config can only raise, never lower, and a policy key may name one verb of a tool (`manage_window.close=ask`) to tighten that verb alone. An approval is bound to the session, expires, and is answered only by an authenticated final transcript; 60 seconds of silence is a denial, and a second identical request while the first is still pending is refused rather than asked twice. A run with no gate fails closed for `sensitive`/`destructive` (the action never executes, and the refusal is itself audited). Decisions land in a local JSONL audit with SHA-256 digests, and permission requests reach the UI on the `lumine.permission` topic.
- **One browser, many agents.** Chromium takes an *exclusive* lock on a user-data directory, so a second process could not launch against the same profile — it failed with Chromium's own paragraph about sessions, which reads like a product fault. Persistent is not optional here (being signed into WhatsApp is the reason the browser exists), so the lock is worked with rather than avoided: the browser is launched with `--remote-debugging-port=0`, the port it actually binds is read from `DevToolsActivePort`, and it is **published** to `<profile>/../browser-cdp.txt`. A later process **joins** that browser via `connect_over_cdp` instead of launching. Three things follow, and all three are load-bearing:
  - **`release` must know whether this process is a guest.** `connect_over_cdp` returns a context whose `close()` tears down the *whole browser* — including a conversation another room is mid-read on. So `_close_remote(shared=True)` stops only its own Playwright client, leaves the endpoint published, and leaves every page alone. The *error* path needed the same guard: `playwright.stop()` on a CDP connection closes the **remote** browser, and doing that in a failure handler means the first error in a joining process kills the browser the owning agent is using. Measured: a holder with nine Chromium processes was at zero the instant a second process failed to attach.
  - **`connect_over_cdp` returns a `Browser`, not a `BrowserContext`.** Everything below the join is written against a context (`route`, `on("page")`, `pages`), so the joined browser's own default context is taken instead. Passing the `Browser` straight through fails one line later with `'Browser' object has no attribute 'route'` — and lands in the handler above.
  - **A guest does not tidy the house.** `_start` used to close every page but the first and clear the WhatsApp tab, which is right for a browser you launched and destructive for one you joined.
  - **A running browser is no longer a reason to refuse.** `whatsapp_probe._already_running` now only refuses a locked profile with **no reachable endpoint** — somebody's own Chromium, or a crash holding a lock nobody releases. That check was also broken: it tried `os.open(..., O_EXCL)`, and on Windows **`O_EXCL` means nothing without `O_CREAT`**, so a genuinely held lock read as free and the check never fired. It now asks the question each platform answers (Windows: deleting a held file fails; POSIX: the advisory file is the signal) and cleans up a stale lock on the way past.
  - Sharing is genuinely concurrent, so the writes that could collide are guarded where the collision would matter: the send ledger holds a key for a confirmed send and five minutes for an uncertain one, and `permission_gate` asks per session.
- **The window fits the screen and keeps the user's theme.** Measured: this machine's screen is 1366×768 and the page reported a viewport of **1422×800** — the window really was larger than the display. Playwright substitutes a viewport and forces `color_scheme="light"`, so it also rendered every site light on a machine set to dark, which is why the browser looked unlike the user's own. Fixed with `no_viewport=True`, `color_scheme=None` (both mean "emulate nothing"), and `_window_args()` sizing from `_screen_size()` — measured once per process via `tkinter`, under a lock, because `Tk()` opens a real window and two LiveKit rooms reaching it at once is two windows fighting over the display server.
- `browse` drives an isolated persistent Playwright profile behind a context-wide route guard: http(s) only, `user:pass@` URLs refused, loopback/link-local blocked unless `LUMINE_BROWSER_ALLOW_LOCAL`, downloads and stored-password access denied, dialogs auto-dismissed, and form-submitting clicks classed `sensitive` so they hit the same approval path as everything else — as is an `Enter` inside a form, since HTML's implicit submission is the same act by another route. Its surface is eight verbs (`open`, `observe`, `act`, `back`, `forward`, `scroll`, `tab`, `close`); `act` takes one reference and the control's own tag decides between clicking, typing, choosing a dropdown option, or pressing a key from a closed list that never reaches the operating system. `browse` and `web_control` are split by *difficulty*, not by feature: `browse` is cheap and ref-based, `web_control` is semantic and snapshot-scoped. Prefer `browse` when the control is visible in an `observe` result.
- **The browser has tabs, and a tab keeps the references it was read with.** `_Browser._tabs` holds every page the model may look at, `_active` names the one it is looking at, and `_page` mirrors it. The old rule for a page the browser opened was to adopt it and **close the previous one**, so a popup was a replacement rather than a second page — "open this in a new tab", comparing two pages, and keeping search results while following a link were all impossible. Every page now becomes a tab: listed, named by number, closable. Three things are load-bearing, and none of them is the list itself:
  - **The document generation is per tab, not per browser.** References are stamped into the document (`data-lumine-gen`) and every action compares against that stamp, so one shared counter means opening a second tab invalidates the *first* tab's perfectly good references — the model is then told to observe a page it just observed. `_Tab.generation` fixes it with numbers still unique across the browser, and the DOM check is untouched: a navigation, a back, or a single-page app replacing its body invalidate exactly as before. Switching tabs deliberately does **not** mint, which is what lets "read tab 1, switch to tab 2, switch back, act on what tab 1 showed" work.
  - **`context.new_page()` raises Playwright's `page` event before it returns** (measured: the event fires while the `await` is still outstanding), so `_on_page` saw the WhatsApp tab as an unregistered page, adopted it as the working page, and closed the page the user had open. `_reserve` reclassifies it afterwards, which cannot miss because it happens after the page object exists. Every messaging call site creates its tab that way, so this was the path and not an edge of it.
  - **Closing the last tab must not reach `_start`.** With no tab left it would launch a *second* Chromium against a profile the first one still holds and fail with "existing browser session" — so "close the last tab" would report the browser as locked. `ensure` opens a blank tab on the live context instead. `MAX_WORK_TABS` is 6, and a refusal rather than a silent eviction when the model asks for one; a page's own popups are capped by giving up a tab nobody is using.
  - One verb, not four: `browse tab` takes its operation in `text` (nothing to list, `new`, a number, `close`), the same shape `scroll` uses for its direction, and parsed purely in `actions.parse_tab_request`. **`web_control` has the same `tab` verb**, because a model that reaches for it and finds no way to open a tab does something worse — it calls `open`, which navigates the tab in use and throws away what the user had. Its page-tab verb was renamed `tabs` → **`pagetabs`** (`tabs` still resolves to it, so nothing existing breaks): one word meant two things, and the collision is removed rather than moved.
  - **The tab parser reads a sentence, it does not match a shape.** The first version wanted an exact word and refused everything else. Measured against what people say, **almost nothing worked**: "delete the 1st tab", "delete the first tab", "close the first tab", "tab 2", "close tab 2", "switch to tab 3", "what tabs", "how many tabs", "next tab", "close this tab", "remove tab 2" — all refused. Three were worse than refused, because they were **silently wrong**: "open a new tab" parsed as a new tab *addressed to the string* "a new tab", and navigated to `https://a new tab`. So the rule is the opposite one: the operation and the target are found **anywhere** in the sentence, ordinals (`1st`, `first`, `2nd`, `last`) and bare cardinals (`two`, `three`…) included, and only what is genuinely ambiguous is refused. **A refusal here is not a dead end** — the model retries, and the retry is where a *second approval card* comes from.
  - **The one refusal is a `close` that named a tab it cannot resolve** — "1.5", "one". Reading those as "the tab in use" destroys a page nobody mentioned, which is the reported failure itself; "one" is absent from the cardinals for the same reason ("no one", "one of them"). `last` is its own marker rather than `-1`, because *the last tab* is a specific tab and *the previous one* is a direction; `+1`/`-1` are resolved against the registry, which is the only place that knows the order.
  - **Reading and switching are `read`; only closing asks.** The test used across `browse` is whether the act changes anything *off* the screen, and switching does not — it changes which of the pages the agent already opened is in front, exactly as `scroll` moves a viewport and `back` walks history. Asking was asking about the agent's own housekeeping, on a voice turn where every card is another second the user is interrupted. `TAB_ACTION_CLASS` lives in `actions.py` and both browser tools import it, so they cannot price the same request differently.
  - **Both tools ask with the same verb.** `permission_gate` collapses two pending cards into one by matching (tool, verb, summary) — and cannot collapse two cards that name themselves differently. `web_control` used to ask with `switchtab` where `browse` asked with `tab`, so a model that tried one and then the other produced **two** cards for one request. That is the "asks twice, answered twice" report, and the fix is one shared `TAB_ASK_VERB`.
  - **`close_others` is its own operation, not a target.** "close the other tabs" destroys several pages and "close the other tab" one; there is no way to know which single one was meant, so the relative reading is the one that never destroys a page the user kept.
  - **Tab numbers identify a tab rather than counting the list**, so a number the model was given earlier cannot quietly come to mean a different page after something is closed — `close 1` leaves 2 and 3, and `switch 1` is then a refusal. The real numbers ride on every read.
  - **A tab request has to reach the browser, and it did not.** `WINDOW_VERBS` contains `switch`, so "switch to the other tab" matched the rule at `classify` step 0 and came back as `manage_window` on the **desktop** — a tool that arranges application windows and has no notion of a tab. The control existed and was unreachable. `TAB_WORDS` now produces a `tab` verb family that returns first, before the window rule, and `Route` grew an **`action`** field: `browse` + `tab` rather than `browse` alone, because `open` and `tab` are both on that tool and the model was guessing `open` — the destructive one. Messaging is the one thing that outranks it ("switch to the WhatsApp tab" names a conversation), which is the same order the rest of the module uses: an explicit claim beats a generic noun.
- **Every read says which tab it read, because asking costs a turn she does not have.** `session.tab_context()` returns the tab number, the count, and the other tabs by title (capped at `MAX_REPORTED_TABS` = 4 — a read is re-billed on every later turn, so a list that grows without limit is a cost, not a feature). It rides on `browse observe`, `web_control read`, `state` and `open`. The reported failure was that Lumine did not know which tab she was on, and the fix that works is not a better instruction to the model — it is that the answer is already in the result, so she cannot act on a tab without having been told which one. And `open` **says when it threw a page away**: it reuses the tab in use, so with other tabs open the result carries "This replaced the page in tab 1… Use 'tab new' next time" — which is precisely the "I need to reload that video manually" symptom, named at the point it happens.
- **A warm-up may keep its own window quiet, and never one the user already has.** `_hid_window` is the guard, and it exists because the first version asked the wrong question: it hid whatever window it found. Measured with a video playing in it — `whatsapp_page(focus=False)` against a browser that was already open and visible left the window **MINIMIZED**, so a background load moved the user's own window out from under them mid-call, which is worse than the popup it was written to remove. `_reveal` clears the flag, so a warm-up that runs after the user has been shown something does not re-hide it one step later.
- **A warm-up must not put a window on the screen.** `prewarm_whatsapp` asks for `focus=False`, which means two things: nothing is brought forward, and a browser that has to be *started* for it comes up minimized. The complaint was a 900×700 Chromium appearing over the desktop while the user was still mid-sentence, on every call and every machine, including ones that never send a message. **Chromium's own `--start-minimized` does nothing here** — measured on this machine, a headed launch with that flag came up `normal` every time, so the window is minimized after the fact over CDP (`Browser.getWindowForTarget` then `Browser.setWindowBounds`), which is a protocol method rather than a guess about window geometry. **Creating a tab raises the window**, measured, so the WhatsApp tab re-hides it after it is created; minimizing after the navigation instead would also have run on the warm path, where the window may be one the user is looking at. `_reveal` is the only thing that un-hides it, and it is required rather than decorative: `bring_to_front` on a minimized window restores it (measured), which is why `browse open`, `switch_tab` and the WhatsApp send flow all still show the user what they asked to see. A browser we **joined** is never hidden — that window belongs to somebody else.
- **Approvals are voice-first.** `runtime/permission_gate.py` speaks the question (`session.say(..., add_to_chat_ctx=False, allow_interruptions=False)`) as well as publishing the card, because a card in the corner of a window is a question a person talking to Lumine will not notice. `add_to_chat_ctx=False` is load-bearing: the model must never read its own approval request back as consent. The card carries the *same sentence* the gate speaks (`question` on the `permission_request` record), because a card that paraphrased the action differently would let someone answer "yes" to one and believe they had agreed to the other. `LUMINE_VOICE_APPROVAL=false` keeps the card and drops the speech — it changes *announcement*, not whether an action is asked for. Hedges ("are you sure?", "what exactly?", "hold on") resolve nothing; withdrawals ("cancel", "withdraw", "never mind") are refusals.
- **Messaging is WhatsApp Web. The installed app is not a messaging path.** `PATH_PREFERENCE = ("web",)` and `backend_candidates()` does not even name `desktop_backend`, so nothing a tool can call reaches `whatsapp_desktop`. It was `("web", "desktop")` with the desktop adapter as a *fallback for `send_text` and `prepare_draft`*, on the reasonable-sounding ground that a working desktop path starts nothing — no browser, no profile, no QR code. It produced three faults, all visible to the user: **two applications for one sentence** (a send whose Web tab had not finished loading fell through, so the desktop app opened and searched its own chat list while Web sat right there — measured in the worker log as a 9.1 s resolve, UI Automation speed); **a resolve that could not be followed by an open**, which came back as "I couldn't read your chat list -- nothing matched" for a chat the previous step had just found; and a silent authority question. The previous mitigation was to pick one path per operation and use it whole; that helps, and the only way to *guarantee* it is to have one path. `ops.supports()` answers from `ONLY_PATH`, not the row's `desktop` field, so a row setting `desktop=True` cannot make the adapter reachable by itself — while the field and `PATHS` stay as the *record* of what the adapter could do, so the next question has a row to point at. **`whatsapp.open_chat` now delegates to `whatsapp_web.open_chat`**, because there were two implementations and they had drifted: only the Web copy had the search-box fallback, so a chat the account has but the virtualised list does not render was unopenable to the send tool. **The installed app is still launchable** — "open WhatsApp Desktop" goes to `open_app` like any other program. An unreachable adapter and a launchable application are different states, and only one of them is gone.
- **The chat header holds the name *and* an accessibility hint, and reading it as one produced a title that matches no chat on earth.** `_JS_ACTIVE_CHAT` used `header.textContent`, and the live header is `div[data-testid='conversation-info-header']` containing a `div` with `'Me2'` **and a sibling `div[data-testid='chat-subtitle']` with `'click here for contact info'`** — so `active_chat()` returned `'Me2click here for contact info'`. That is the dangerous direction: `open_chat` refuses a title that mismatches *on purpose* (a mismatch means we would type into somebody else's conversation), and a title that can never match turns that check into one that **always refuses**. Measured: the chat was open, `open_chat` returned `False`, and the send died on "I couldn't read your chat list" for a chat the previous step had just found. The reader now takes the first child that is not the subtitle, and names the exclusion rather than `replace`-ing the hint's wording — WhatsApp localises that string, so a non-English UI would get the concatenated title back and the same permanent refusal. `test_whatsapp_web.ChatHeaderReaderTests` keeps the measured header as a literal fixture.
- **A saved contact and a chat row are different shapes, and the reader only knew one.** WhatsApp's search box matches **contacts who have never been messaged**, and renders those differently: measured, `cell-frame-title` is `'Jubayed Reza (22-23)'` — the name *and* the phone number — while a chat row is just `'Me2'`; and `cell-frame-primary-detail` is `''` on a contact row where a chat row holds the timestamp. The name and the number share **one text run**: walking the title cell found five nested elements each carrying the whole string and no boundary between them, so it cannot be read structurally. Three failures came out of that one fact. **The row could not be clicked** — `_JS_MARK_ROW` compared the raw cell against the name, so `"Jubayed Reza"` never matched. **A correct chat looked wrong** — the header renders the same `'Jubayed Reza (22-23)'`, and a mismatch is *refused*, so the user watched the conversation open and was told it did not. **The digits read as a group size** — `participants` looks for a small element whose whole text is 1–4 digits, and "22"/"23" are exactly that, so a person was refused as a group (the "Me2" bug in a new hat). `lumineContactName` strips a *trailing* parenthesised run that is entirely a phone number — at least four digits plus a separator, or seven digits — so `'Team (2024)'` keeps its brackets and getting it wrong is a safe refusal rather than an invented name. **One definition, three readers**: the chat rows, the row marker and the header all call it, because a reader that strips and a marker that does not is exactly the pair that made this invisible. `active_chat_names()` returns `(name, as displayed)` and `open_chat` accepts either, so the rule never has to exist in Python as a second copy.
- **Search results are not chats, and the reader believed they were.** WhatsApp searches message *text* too, and those rows carry a `cell-frame-title` too — so `'Ok, I won't send you any other messages'` came back as a contact's name for the query "Me". Worse than a missed contact: a bogus candidate makes `choose` report "more than one chat matches" for a name with exactly one contact, and `open_chat` would try to click a message row. The discriminator is structural — a message result carries a `chatlist-message-<hash>` cell (`chatlist-message-3EB0BE8E693D9F711AB8BF`) and nothing else does — and it is refused inside `lumineChatRow`, so the plain list read and the search read cannot disagree about what a row is.
- **The search pre-filter was a spelling test, and speech is not spelled.** `_JS_FILTERED_ROWS` dropped any row whose title did not contain the query verbatim. The account holds `Jubayed Reza`, the request said `Jubayat`, and `'jubayed reza'.includes('jubayat')` is **false** — one letter, and a contact demonstrably on screen reported as absent. Matching is `whatsapp_flow.match`'s job, so the pre-filter was removed rather than loosened. A fourth tier was added there: exact, prefix, containment, and last *the same words heard differently* — **every** query token must find a near-partner (≤1 edit at 4–5 chars, ≤2 above), tokens under four characters are never fuzzy, and it still loses to containment so a literal match is never displaced. It fires because `'jubayat'`/`'jubayed'` is 2 edits. `choose` still asks when two rows tie, which a fuzzy tier makes likelier, not less.
- **"Did the filter land?" needed two signals, and the box must be cleared on the way *in*.** The structural signal is a section header — search results are grouped under 'Chats' / 'Contacts' / 'Groups', and a header is a `list-item-*` row with **no** title cell (`list-item-0` was `'Contacts'` with `cells: []`); those never exist in the unfiltered list. It is not sufficient alone: while the box is being *cleared* the headers are still up over the unfiltered list for a frame or two, so `applied` can fire before a character has matched. Paired with "the rows differ from the pre-search baseline", which is only meaningful now that **both** reads are capped at 40 — the old 12-cap made twelve rows of an unchanged forty a strict subset, so an unfiltered list passed the baseline test on its own. And clearing on the way *out* was not enough: the box arrives dirty (a person typed in it, or an interrupted search never cleaned up), the query is *appended*, WhatsApp matches nothing, and four searches in a row report contacts absent while the earlier result sits on screen behind them. It is now emptied and **verified empty** before typing — verified, because assuming the keystrokes worked is the same class of assumption that made an empty composer read as holding a draft. Measured: the dirty-box search went from reporting seven baseline chats to `['Jubayed Reza']` in 1.18 s.
- **Two of the fixes were invisible to the test suite, and both were mine.** Concatenating a helper function in front of an arrow function re-creates the exact `SyntaxError` this file already documents (`function f(){…}` followed by `(x) => {…}` parses as `f(){…}(x) => {…}`) — and `_with_chat_row` does not append the closing brace, so a body that forgets it is *also* unbalanced. Either way the script did nothing at all: `open_chat` returned `False` for chats that opened perfectly well by hand. A third was returning `_poll`'s `(applied, rows)` tuple where callers expected a list. All three were caught only because the fix was checked against the live account, not because a test went red. `test_whatsapp_web.ScriptShapeTests` now balances the braces of every wrapped script and asserts each one is a single parenthesised expression — not a JavaScript parser, but it catches the mistake that keeps being made.
- **An unreadable header no longer costs the whole window.** A contact who has never been messaged has no conversation header, so the open step used to run to its 4-second deadline before proceeding on the documented *refuse-on-mismatch / proceed-on-unreadable* rule. The composer is now polled in the same breath: it is a positive signal rather than an absence, and a message box is precisely what the rule was already leaning on. The mismatch refusal still runs first. Measured: opening a never-messaged contact went from 4.94 s to 1.29 s.
- **There were two readers of "is WhatsApp signed in", and the send path asked the worse one.** `whatsapp.py::whatsapp_state` looked at `#pane-side` **once** and called everything else `"logged_out"`. `whatsapp_web.state` polls and reports `loading` as its own answer. `web_backend.check()` called the first, so on a cold tab — several seconds of splash, which is exactly what the pre-warm exists to cover — a **signed-in** account was told *"Scan the QR code once in Lumine's browser window"*, for a code already scanned. Messaging being Web-only made it worse: there was no second path to quietly try instead. Two fixes, both structural: `whatsapp_state()` **delegates** to `whatsapp_web.state` (the old script is kept as `_JS_STATE_REMOVED`, named rather than silently deleted, so "we removed the naive one" is the useful fact), and `check()` gives each of the three states **its own sentence** — `loading` says *still loading, give it a moment*, and only a real QR code asks for a scan. Every state names the remedy for *its own* state, because the whole cost of guessing wrong here is sending the user to do something that was never the problem.
- **The composer shortcut fired on the *previous* chat's composer.** Removing the 4-second wait for a chat with no readable header (a contact who has never been messaged has none) introduced a faster way to be wrong: the instant after a row press, the conversation that was open before is still fully on screen, so "a composer exists" said nothing about whether the *right* conversation opened — and the next step types into whatever is there. The user's symptom was its milder cousin: the first attempt after a different chat reporting failure or success inconsistently, and the second attempt working, because by then the DOM had settled. Fixed by `_HEADER_GRACE_SECONDS` (1.2s): the header gets a grace period to become readable on its own — the better answer when it does — and the composer is only believed once the page has had time to swap. `test_whatsapp_web.HeaderGraceTests` drives it with a fake clock and asserts the first composer check is at or after the grace period, that the wait is still well under the old timeout, and that a **mismatched header refuses without ever asking about the composer**.
- **The name gets typed into the search bar twice in one send.** `send_whatsapp` resolves with `search_chats` (which types it), then `open_chat` searches for it again — so a contact who is not in the rendered list has their name typed twice, visibly, in a single turn. `_search_then_click` now empties the box first, the same guard `search_chats` uses, which also removes the append hazard (`JubayedJubayat` finds nothing) on the second pass. `_empty_search_box` is now shared by both, so "one clean pass over whatever was there" is a property of the helper rather than of each call site remembering.
- **The WhatsApp pre-warm is gone, and it was racing the tool it was meant to help.** `prewarm_whatsapp` ran as an un-awaited task on the *same* `_Browser` singleton the messaging tools drive, so a request arriving while the warm-up was still navigating found a tab that existed and was not yet usable. WhatsApp renders the search box and the composer **last**, so `_focus` found nothing or found an input the SPA was about to replace, the keystrokes went into a control that no longer existed, and the report was "I couldn't read your chat list" for a contact that was right there. Retried, it worked — which is the whole of "it takes several attempts to find the contact". It also opened a tab per session before the user had said anything. `whatsapp_page()` waits properly now, so the first request is a few seconds slower and **correct**; a visible pause beats a message sent into a chat that may not be the one.
- **The steps that *act* wait for the page; the steps that only look must not.** `search_chats`, `type_message` and `press_send` call `require_ready()` first. `search_chats` typed into a page that might still be a splash screen; `type_message` asked "is there a composer?" of a page that had not drawn one and refused with "I can't see the message box" for a chat that has one; and `press_send`'s Enter fallback types into **whatever currently holds focus**, which on a mounting page is the search box — a send gesture aimed at a search field, which is worse than no send because it looks like it worked. `active_chat` and `active_chat_names` deliberately do **not** wait: `open_chat` polls them in a loop, and a readiness poll inside that loop would take the full 90 seconds on every refusal. The distinction is *acts versus looks*, not a list of functions.
- **The blank first tab is adopted rather than left beside WhatsApp.** Starting the browser leaves one page, blanked to `about:blank` on purpose ("a persistent profile must not mean persistent tabs"), and `_start` registers it like any other tab. When the first thing anybody asks for is WhatsApp, that page is dead weight and the user sees a window with an empty tab next to WhatsApp. `_adoptable_blank_page` takes it, and `_forget_tab` drops it from the registry first — `_reserve` treats an already-registered page as done, so without that the adopted page would still be listed as tab 1, blank, for a model that never asked for it. Safe because a blank page has no document, so there is nothing in it that could carry a `data-lumine-ref`; that is also why the obvious check ("is it a registered tab?") refuses, since `_start` does register it. Only when it is the **only** tab, and never on a browser we *joined* — a blank page in somebody else's browser may be the tab they just opened.
- **A header that mismatches is only evidence once the page has settled, and the user is the one who proved it.** The symptom was specific and reproducible: *"only happens when another chat is open and I say her to search another contact and send a message to that"* — she searches, opens it, reports she cannot, and a second request (when the chat is already open) works perfectly. The sequence is: press B's row, read the header, and the header **still says A**, because the previous conversation has not been swapped out yet. A mismatch read in that instant is not evidence of the wrong chat, it is evidence that we have not looked yet — and refusing on it discards our own successful click. `_HEADER_GRACE_SECONDS` therefore gates the **refusal** as well as the composer shortcut: a readable, mismatched, *settled* header still refuses immediately, and only the in-flight window is forgiven. The second attempt always worked because by then the page had settled, which is the tell.
- **The send confirmation is spoken by the *product*, once — and two earlier fixes were both wrong in the same way.** The user heard it twice: *"the message has been sent"*, then *"I already sent that message to X"*. Nothing in this codebase speaks after a send — `permission_gate._announce` speaks the **question** before the action, and the failure apology is a separate thing — so **both lines came from the model**, one per fact it was handed: a step line saying the message was going out, and a return value saying it had gone. Two facts about one event, and a model asked to report on a turn says both. Fix one was deleting the step's `verified` detail; fix two was deleting the send step entirely. Both were wrong in the same way, and the user's objection to the second is the useful part: *"you deleted the voice that said to confirm the send request."* The confirmation was never the problem. **The speaker is.** So `web.announce_sent` now speaks it from code — `voice_line.speak_line`, at the moment delivery is *observed* rather than reported — and the result tells the model it has been said, so its own reply adds nothing. `SEND_STEPS` is 5 and the list ends at the approval question, because the answer to that question *is* the send. The channel is reported rather than assumed: `SAID` when a synthesiser carried it, `SILENT` when the profile owns none — which is `gemini-3.8-live`, where `say()` raises, so the model's own reply to the *result* is the only voice there is and the result says *"say this once, in your own words"* rather than the false *"you have already said it"*. A **third** fix was needed, and it was the same mistake in a new place: `speak_line` escalates a line to the realtime model with `generate_reply`, and doing that here does not *be* the confirmation — `announce_sent` runs one statement before the tool returns, and the return is what makes the model speak (LiveKit regenerates for any non-empty return, and a realtime model with server-side turn detection replies whether or not a reply was asked for). So the injected sentence and the model's own reply were two statements about one send, and *"the message has been sent"* came back. `announce_sent` now passes `allow_model=False`, which refuses the fallback and answers honestly `SILENT` on a profile with no synthesiser. `SEND_STEPS` is 5 and the list ends at the approval question, because the answer to that question *is* the send. `OneConfirmationTests` and `AnnounceSentTests` pin it: spoken once on a profile that can speak, never *through* the model where it cannot, and the step list ending at the question with `SEND_STEPS` matching the steps that actually fire.
- **`send_whatsapp` resolves a recipient in two steps (candidate list first, exact match second) and sends only to chats that already exist on the account.** `LUMINE_WHATSAPP_MODE` is `off`, `deeplink` (default: opens a `whatsapp://` draft — **the user presses send**), or `automation` (opt-in, classed destructive). When neither path is ready the refusal names every path's own reason and says "Nothing was sent." exactly once; a send is only confirmed by an observation taken *after* the attempt (stale readings never count), and an unconfirmed or dirty composer holds the ledger like an uncertain send. An unrecognised mode is `off`. Its send ledger holds a confirmed key for 10 s and an *uncertain* one for 5 minutes, so a send whose outcome is unknown is never attempted twice.
- **Every WhatsApp operation runs on `whatsapp_web.py`, and the send flow types before it asks.** That module carries reads, attachments, reactions and chat management as well as sending, because it is the only path with a DOM — and an accessibility tree offers geometry and heuristics where a DOM offers identity. `whatsapp_desktop.py` (UI Automation, one worker thread, capability recomputed per call and never cached) remains in the tree as the record of what the adapter could do, and is unreachable from any tool. `choose_backend(verb)` still filters by the operation table before asking, so a verb the Web path cannot do is reported as such rather than as an unreachable application.
- **The order of a send is resolve → open → draft → ask → send → confirm, and the draft is the point.** In automation mode the text is typed into the chat and *read back out of the composer* before the approval question, so what the user is asked to confirm is on their own screen rather than inside a sentence Lumine said. `Backend.draft` returns whether the composer holds exactly what was asked for, and a draft that lost its tail is cleared rather than sent or left for a person to press send on. A declined approval clears the draft — otherwise one "no" would make every later send refuse with "there is already something written there".
- **Reading message history is a separate tool with its own consent.** `whatsapp_read` is the only tool that shows the user what other people wrote, `messaging.whatsapp.history` is `off`/`ask`/`auto` and **defaults to `ask`**, and the question is asked *before* the chat is opened — asking afterwards would have already done the reading. The grant is session-scoped, so the question says out loud that it lasts the rest of the conversation, and it is released with the session. `off` means off rather than degrading into a question. Everything a read returns is wrapped with `tool_results.wrap_untrusted`, which matters more here than for any other tool: a message is text a third party wrote, and a contact is a stranger who can put "ignore previous instructions" into one.
- **`agent/tools/messaging/whatsapp_ops.py` is the operation table, and everything reads it.** One row per verb — class, which paths can do it, how it proves it happened, and whether an unconfirmed outcome holds the retry. `TOOL_ACTION_CLASS` is *computed* from it (so the Tools-page badge cannot promise less than the gate enforces), `choose_backend` filters by it, and `test_whatsapp_ops.py` pins the three ends together. Every verb has a `verify` clause and a miss is always a refusal: a broken selector must degrade to "I couldn't find the message menu", never to a plausible wrong action. `agent/whatsapp_probe.py` reports which selector is live in the current WhatsApp build, which is how those lists get maintained from evidence rather than recollection.
- **What the live WhatsApp DOM actually is, measured — and it is not what the selectors assumed.** `agent/whatsapp_probe.py` reads a chat with an empty composer; `agent/whatsapp_message_probe.py` types into a live one, because the send button and the bubbles do not exist until then. Two findings are load-bearing:
  - **Message rows carry hashed class names** (`x1liijdw xu342n7 xelbjmh …`) and no `data-id`, so `div.message-in` / `div.message-out` match *nothing* and adding spellings cannot fix it. All six scripts that addressed a message used them, and every symptom was silent: reads returned nothing from a chat full of messages, and `delivery_seen` could never confirm a send. That second one is the whole of "she cannot send even after I said yes" — the send worked and the *confirmation* was blind, so the ledger then held the retry for five minutes.

Treating the row as the bubble is what made a real chat read as empty. **Direction is bubble centre against *pane* centre**, never the viewport: the pane starts at x=491 of a 1422px window, so a viewport midpoint puts every message in the left column and a sent message becomes indistinguishable from a received one.

There was a structural fallback ("the narrowest descendant carrying the row's text") and it was measurably wrong: the encryption banner has no `msg-container`, the fallback matched some element of it, and an empty chat reported one *delivered* message. If a future build drops the attribute, the honest answer is an empty read — a refusal, not a plausible wrong one.
  - `_with_rows` exists because Playwright evaluates a string argument as a **single expression**, so a helper cannot be concatenated in front of an arrow function: the page parses `function f(m){…}` followed by `(x) => {…}` as `f(m){…}(x) => {…}` and answers `SyntaxError: Malformed arrow function parameter list`. That happened, and it read as a broken tool.
- **A click inside the page is not a click.** `element.click()` from `evaluate` dispatches an *untrusted* event: the page's own listeners run and none of the browser's defaults happen, which for WhatsApp's framework-driven chat list is nothing at all. The probe showed it exactly — `Chat: <name> (opened: False)`: a click reporting success with no conversation ever opened. Rows and menu triggers are now **marked** with a data attribute and clicked by Playwright, which is the same reasoning `browser/actions.py` applies to keystrokes. This was the real cause of "she can search but cannot select".
- **A belief about the page waits for evidence.** The sign-in check read the page once, immediately after navigation, and called anything without a chat list "signed out" — so a fully signed-in account was reported as signed out *and* all 17 selectors missing, while the same profile sat logged in in another tab. WhatsApp is an SPA with seconds of splash screen. `state()` polls and reports `ready` / `logged_out` / **`loading`** separately; `loading` never becomes a claim about sign-in, because telling a signed-in person they are signed out sends them to re-scan a QR code that was never the problem. Cold starts need ~90s (`READY_TIMEOUT_SECONDS`), not 30.
- **A diagnostic must hand the browser back, on the event loop that created it.** `whatsapp_probe.probe()`, `whatsapp_send_probe.run_and_release()` and the message probe all release in a `finally` *inside* the single `asyncio.run`. The release alone was not enough: an earlier shape ran `asyncio.run(run(...))` and then, separately, `asyncio.run(release())` — two loops in one process, and Playwright's objects belong to the loop that made them. The visible cost was a wall of noise **after** every successful run: `RuntimeError: Route.continue_: Event loop is closed`, `Task was destroyed but it is pending!`, `EPIPE: broken pipe, write`, a Node stack trace. It reads like the tool failing when it had already printed `SENT AND CONFIRMED`. Zero of it remains once the release happens before the loop closes. **It was ours, and it was not suppressible noise — it was a second event loop.**
- **The Send button was never actually being pressed.** `TARGETS["send_button"]` listed `button[data-testid='send']` and `[data-icon='send']`; measured against a live draft, **neither matches**, so `hasSend` was always False and every send silently took the Enter fallback. That fallback is sound — Enter is WhatsApp's own send gesture and is locale-independent — but it meant the "clicked a live control we verified" property the module claims was not being exercised at all, and `press_send` could not distinguish "the button is not there" from "the button is there and inert".
- **"WhatsApp" means WhatsApp Web; the desktop app has to be named.** `router.py` splits what used to be one table: `DESKTOP_SITE_APPS` (an installed app is the better answer to "open X" — Instagram, Netflix, Spotify) and `WEB_FIRST_SITE_APPS` (WhatsApp, where it is not). Two rules combined to open *both* windows for one sentence — the site table preferred the installed app, and the messaging rule claimed anything naming "whatsapp" — so each was correct and the pair was not. Only `"desktop whatsapp"` / `"the whatsapp app"` reach `open_app`; a bare mention reaches the Web-backed messaging tools. `"message her on my desktop"` still sends, because that phrase names the machine and not the program. On a machine without the app installed the word falls back to Web rather than refusing: the user asked for WhatsApp and the qualifier was unhonourable, but the thing they wanted is openable.
- **Every click into WhatsApp is a real Playwright press**, and twelve were not. Chat row, composer, send button, message menu, menu item, confirmation, emoji, row menu, block control, linked device, call button: each was once an untrusted `el.click()` or `dispatchEvent` from inside the page, and each reported success while doing nothing. `element.click()` runs the page's own listeners and none of the browser's defaults — so a menu closed before it could be read and a row did not open. They are now **marked** with a `data-lumine-wa-*` attribute and pressed by Playwright, and `test_whatsapp_web.ClickFidelityTests` asserts no script contains `.click()` or `dispatchEvent` at all.
  - **A mark must be cleared before it is set, or it redirects the next press.** This was the bug behind "she can select the chat but cannot type", and it was invisible from the code: every press marked its element with `data-lumine-wa-focus='1'` and asked Playwright to click `[data-lumine-wa-focus='1']` — and nothing ever removed the attribute. So they accumulated. Resolving a name focuses the **search box**, leaving the attribute on it; focusing the composer marked a *second* element; `querySelector` returns the **first** match in document order, so every press landed on the search box. Then the confirmation asked whether the *composer* had focus, and it never could. Measured: `composer()` read the box fine and `type_message` refused ~200 ms later with "WhatsApp's layout has changed and I couldn't find the message box" — on every chat, every time, with nothing about the layout having changed. Every marker now clears all others first, via `_JS_MARK_ONE` or an inline loop, and `StaleMarkerTests` pins it. `data-lumine-wa-row` is the sharp end: the Web open step and the send path both use it, so opening a chat then sending to a different one pressed the first row — a message prepared for one chat and pressed on another.
  - `_focus` **confirms** focus landed, because a `contenteditable` can absorb a press and still not be editing, and typing into that sends the message to the search box, a menu or the page body. A real press is tried first; `el.focus()` is the fallback for when Playwright's actionability check refuses an overlaid composer.
- **The composer is verified after typing, and the emptiness test is the whole of "she can select the chat but cannot type".** `type_message` reads the box back and clears it if the text did not arrive intact, rather than asking the user to approve a truncated draft. The reason it could be truncated: React re-renders the composer per keystroke, so `KEY_DELAY_MS` paces the keys and the verification is the guarantee. And the emptiness test had drifted from the comparison helper — the JS stripped two of the six characters WhatsApp pads a `contenteditable` with, so an **empty** box read as holding a draft and `type_message` refused on it, on every chat, forever (`text=''` while `empty=False`, measured). Both now come from one `_INVISIBLE` list, and a test compares the two languages.
- **The chat list is read from `cell-frame-*` test ids, and `group` is three-valued.** A live dump of the account's own list showed rows shaped `<div role="row" data-testid="list-item-0" class="x10l6tqk …">` containing `cell-frame-title`, `cell-frame-primary-detail` and `cell-frame-secondary`, with **no `data-id` on any row**. The old reader used `span[title]`, `data-id` and `[data-testid="last-msg"]` — none of which exist — so every chat came back with an empty `jid`, an empty `preview`, `group: false` and no unread count, and none of it announced itself. `_JS_CHAT_ROW_FN` is now the single row reader shared by browse and search, because the search path used to hard-code `preview: ''` and `unread: 0`, which made "has Afia replied?" resolve the name and then come back with nothing to say.
  - **`group` is `true` / `false` / `null`, and `null` is treated as "possibly a group."** With no JID there is no way to tell, and the four call sites that read `"group" if row.get("group") else "contact"` turned *could not tell* into *permission* — quietly switching off the rule that a group is never substituted for a person. `whatsapp_flow.kind_for_row` carries the third value through and `ChatCandidate.maybe_group` asks rather than guessing.
  - **A participant count is a separate element, never a regex on the name.** `title.match(/(\d+)$/)` classified the real contact **"Me2"** as a two-person group, which would have refused to message a person by the shape of their name. A count lives in its own element inside `cell-frame-title`; a person's name is text.
  - **The list is virtualised** — four rows existed against an account with many more chats — so `read_chat_list` reports `partial` and `unreadReadable`, and the tool passes that to the model. An empty unread result must not read as "you have nothing unread" when no badge was visible at all.
- **Focus is reached two ways and *verified* either way.** A real Playwright press is tried first, but measured against the live account it **times out** on the composer: something overlays it and the actionability check refuses rather than clicking through. That produced "WhatsApp's layout has changed and I couldn't find the message box" on a chat that was open and whose composer the same function had just read. `el.focus()` is the fallback; the confirmation — `el === document.activeElement || el.querySelector(':focus')` — is what decides, because a `contenteditable` can absorb a press and still not be editing, and typing into that sends the message to the search box or a menu.
- **A path from the model cannot attach a file from outside an allowlisted folder.** `agent/tools/messaging/whatsapp_files.py` resolves the path *first* and compares against resolved roots (`LUMINE_ATTACH_ROOTS`, defaulting to Downloads/Pictures/Desktop), so `..`, an absolute path and a symlink out are all judged by where they land. Extensions are a whitelist and a URL is refused outright, because downloading would mean lifting `accept_downloads=False`. Only the file *name* and size reach an approval card, never the directory layout.
- **Steps are visible.** `agent/runtime/progress.py` lets a tool narrate what it is doing, so a six-stage send is a sequence the user can follow rather than several seconds of silence. Steps publish on `lumine.tool` as `tool_status` with an `action`, and are told apart from whole-call records by that field rather than by their status. Nothing in that module may raise: a telemetry channel that can end a send is worse than no telemetry.
- **`agent/agent.py` pre-warms the WhatsApp tab** as a background task while the greeting is being generated. Starting Chromium and loading WhatsApp Web is several seconds and happens on the first messaging request of every conversation; paid during the greeting it is invisible. It is never awaited and its failures are dropped — a machine with no signed-in WhatsApp must not stall every session.
- **Contact search goes through WhatsApp's own search box**, not the rendered chat list — `tools/messaging/whatsapp_flow.py` plus `search_contacts` in the desktop adapter and `search_chats` on the Web path. The rendered list is the last few dozen conversations, which is why a name used to resolve only when the chat happened to be on screen; the search box reaches the account's whole history. A result is believed only once the list stops looking like the pre-search baseline, and the box is cleared in a `finally` because a filter left behind narrows every later lookup. A **group is never auto-selected for a person**: it is read from the row's participant count, not from its name. `DraftApproval`/`DraftState`/`ContactFlow` in that module are tested but **not** on the send path — see its docstring before wiring them in anywhere.
- `agent/tools/tool_results.py` owns the one rule for what a tool may return: a central `MAX_RESULT_CHARS` ceiling, keyed JSON rather than prose, a truncation marker, and a delimiter around anything retrieved from the internet. New tools go through it — a tool result is re-sent on every later turn, so its size is paid for repeatedly.
- `agent/tools/apps.py` makes a launch **idempotent for `LUMINE_LAUNCH_DEDUP_SECONDS` (default 10, `0` disables)**, because one `launch()` starts exactly one process and a second window therefore means the tool was called twice — two identical function calls in one turn, which no interruption setting can see. The suppression is keyed on `launch_key()` (`Notepad` / `notepad` / `notepad.exe` are one app), is released if the launch failed so a retry still works, and logs `[open_app] suppressed a repeat launch of …`. It is tool-level because there is no provider-level alternative: `parallel_tool_calls: False` is cascade-only, and the Gemini Live realtime models expose no such switch.
- `agent/prompts/persona.md` is the **full** persona, read on demand by `recall_persona`. `persona_core.md` is what every request carries. The split is about when the persona is read, never what it says; `agent/tests/test_persona_split.py` asserts the full file survives.
- `agent/runtime/context_trim.py` trims the chat context to `LUMINE_MAX_CONTEXT_ITEMS` (default 40, floor 24) on `conversation_item_added`. It is a backstop — `ChatContext.truncate` preserves the system message, which is the persona and the tool policy.
- `agent/runtime/llm_errors.py` classifies a failed LLM call, and `agent/runtime/failure_gate.py` opens a circuit after three consecutive failures. Lumine speaks one short apology per opening. Do not add a retry loop: a rate-limited session that keeps trying spends the quota it has left.
- Notices reach the UI on the `lumine.notice` data channel, not only on stdout — a notice that depends on how the process was started is a notice that silently does not arrive.
- **Never let a telemetry write raise.** `runtime_events.write_event_line` catches `OSError`/`ValueError` for exactly this reason: the desktop app pipes the worker's stdout, and a write to a dead pipe raises `OSError: [Errno 22] Invalid argument` on Windows. That unguarded `print` was killing every session on its first line. `agent/broken_stdout_check.py` reproduces it.
- `agent.py` sets `logging.raiseExceptions = False`. LiveKit's logger fails on the same broken stream, and without this every log record prints a full traceback.
- The Rust side sets `LIVEKIT_LOG_LEVEL=info` on the child unless already set, because `agent.py dev` enables LiveKit's DEBUG level and a desktop app should not have to swallow that through an OS pipe.
- Do not insert a module-level `def` into the middle of a class body in these modules. It silently truncates the class — `RuntimeEventPublisher.emit` vanished that way and every session died on an `AttributeError` while all the writer's unit tests still passed. `test_stdout_resilience.PublisherSurfaceTests` guards it.
- Tool payloads are delivered to the **stage ledger** via `onToolResult`, never through `ConversationToolEvent`. Keep it that way: a retrieved page rendered inline in the transcript reads as though the model had been handed it by the user, which is the shape a prompt injection wants.
- `GROQ_MODEL` defaults to `openai/gpt-oss-20b`; `llama-3.3-70b-versatile` and `llama-3.1-8b-instant` are Enterprise-only as of August 2026 and are marked deprecated in the catalog. `GROQ_REASONING_EFFORT` defaults to `low`, and `max_completion_tokens` to 900 — GPT-OSS is a reasoning model, and thinking is drawn from the same budget, so a low cap produces an internal monologue and no audio.
- Keep network tools bounded to short, user-facing results and keep `open_app` shell-free and restricted to validated names. Tool tests exercise parsing/formatting/permissions locally; do not make the test suite depend on live external services.

## Setup and local commands

Use an existing repository `.venv` when possible. From the repository root:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r agent\requirements.txt
```

Create ignored local config files from `agent/.env.example` and `lumine-ui/.env.example`, then fill in real values. Every credential line in the example ships **empty**, and an empty line is a real absence -- a `your-…` placeholder reads as a working key to every presence check, which is the same class of bug as the credential-injection one. `agent/tests/test_env_example.py` derives the credential list from the catalog, so it fails when the file and the code disagree.

The default pipeline is `gemini_live`, so a working install needs **LiveKit's three values plus `GOOGLE_API_KEY`** -- four entries, one provider. Groq and Cartesia are only needed for `LUMINE_PIPELINE=legacy_cascade`; `GROQ_MODEL` is optional and defaults to `openai/gpt-oss-20b`.

```powershell
# terminal 1: Tauri plus its Vite dev server. It starts the Python worker itself
# (start_agent + wait_for_agent_worker) and injects the keyring credentials.
Push-Location lumine-ui
npm ci                 # first checkout or dependency reset
npm run tauri dev
Pop-Location
```

To run the worker standalone instead — useful when debugging the worker alone —
use `.\.venv\Scripts\python.exe agent\agent.py dev` in a second terminal. Do not
leave one running while testing settings changes: the app cannot see it, and
LiveKit dispatches a room to a single agent, so the worker that answers may not be
the one holding your saved config.

`npm run tauri dev` starts Vite itself on strict port `15173`; do not start a second Vite server on that port. The port is `15173` rather than the Tauri-conventional `1420` (and no longer `5173`) because Hyper-V/WSL redraws 100-port exclusion blocks inside the Windows dynamic port range (`1024-15000` here) on every boot — `1420` fell to `1351-1450`, `5173` to `5156-5255` — and binding an excluded port fails with `EACCES`, not `EADDRINUSE`. `15173` sits above that range, so it survives the redraw. `npm run dev` is useful for the UI only, but Tauri `invoke`/microphone flows require the Tauri app. Tauri resolves Python in this order: `LUMINE_PYTHON_BIN`, `VIRTUAL_ENV`, the repository `.venv`, then `python`/`python3`. `LUMINE_AGENT_PATH` and `LUMINE_AGENT_ARGS` affect the Rust worker manager.

For focused LiveKit helper debugging, run `agent/livekit_token.py <room> <identity>`, `agent/livekit_dispatch.py <room> <agent_name>`, or `agent/livekit_room.py <room>` with the repository Python environment. These helpers load `agent/.env` themselves. `agent/multisession_check.py` dispatches three sequential sessions at one running worker and reports whether all three start — use it when a session joins once and then never again. `agent/broken_stdout_check.py` starts a worker whose stdout is a dead pipe and asserts the job still starts.

Both check scripts kill the process tree on exit. Stop any leftover `python agent.py dev` before running either: a worker left registered as `lumine` absorbs the next run's dispatches, which looks exactly like a broken worker.

## Environment and security boundaries

- The only frontend-safe LiveKit variable is `VITE_LIVEKIT_URL`; `VITE_LUMINE_DEBUG_EMOTION=true` enables frontend emotion diagnostics, while backend `LUMINE_DEBUG_EMOTION=true` enables agent-side emotion logging. Never put LiveKit, Groq, or Cartesia secrets in a `VITE_*` variable or commit `.env` files; Tauri invokes the Python helpers so credentials stay out of the browser bundle.
- Keep LiveKit/provider details behind the Tauri/`features/voice` integration boundary and presentation components backend-agnostic. Preserve the local-first goal and the persistent Python worker; do not replace the desktop app with a cloud-only service.
- Preserve the persona in `agent/prompts/persona.md`, the light/dark `AppearancePreset` contract in `lumine-ui/src/pages/home/constants.ts`, and the existing SVG-based avatar engine; these are product contracts, not incidental styling.
